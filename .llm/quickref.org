** Important Decisions (TL;DR)

| Decision | Choice | Why |
|----------+--------+-----|
| Base | Fork ElixirScript | 80% done, proven architecture |
| Output | ES Modules only | Modern standard, simpler |
| AST | BEAM debug_info | Macros pre-expanded |
| Patterns | Runtime library | Easier to implement correctly |
| Atoms | Symbol.for() | Perfect semantic match |
| OTP | Not supported | Reduces scope, not needed client-side |
| Coverage | ~30% stdlib | Pragmatic, achievable |

See =decisions.org= for full rationale.

** What's Supported (Target)

*** Data Types ✅

- Integers, floats
- Strings (binaries)
- Atoms
- Lists
- Maps
- Tuples
- Structs

*** Language Features ✅

- Modules (=defmodule=)
- Functions (=def=, =defp=)
- Pattern matching
- Guards
- Pipe operator (=|>=)
- Control flow (=if=, =case=, =cond=, =with=)
- Comprehensions (=for=)
- Try/rescue/catch
- Protocols (basic)

*** Not Supported ❌

- GenServer, Supervisor, Task
- spawn, send, receive
- Most OTP constructs
- Macros (use pre-expanded AST)
- Some stdlib functions

** Common Questions

*** Q: Can I use this in production?

A: Not yet! Wait for =curupira_script= v0.33.0 (Q1 2025).

The template works but uses old ElixirScript (2018).

*** Q: Why not Phoenix LiveView?

A: LiveView is server-rendered. Curupira is for client-side SPAs.

Different use cases!

*** Q: Will it support React/Vue?

A: Not built-in, but you can integrate.

We'll provide examples later.

*** Q: What about OTP?

A: No GenServer/Supervisor. Too complex, not needed for client-side.

Basic Agent support only (synchronous, no real processes).

*** Q: Can I share code with my backend?

A: Yes, if it doesn't use:
- OTP (GenServer, etc.)
- Unsupported stdlib functions
- receive/spawn

Common business logic works fine.

*** Q: How big will the bundle be?

A: TBD. Depends on what you use.

ElixirScript runtime was ~100KB (before minification).
With tree-shaking, could be much smaller.

** Performance Expectations

*** Compilation Speed

Target: < 5 seconds for medium projects (50 modules)

ElixirScript was slower. We'll improve with:
- Better caching
- Incremental compilation
- Parallel processing

*** Runtime Speed

JavaScript is slower than BEAM for:
- Recursion (no tail-call optimization)
- Pattern matching (runtime library overhead)
- Large data structures (immutability overhead)

But fine for typical client-side work.

*** Bundle Size

Depends on usage. With tree-shaking:
- Small app (~10 modules): ~50KB runtime + code
- Medium app (~50 modules): ~100KB runtime + code
- Large app (~100+ modules): ~200KB+ runtime + code

These are estimates. Will measure after implementation.

** Debugging Tips

*** Compilation Fails

#+begin_src shell
# Check versions
elixir --version  # Need 1.17+
erl -version      # Need OTP 26+

# Clean and retry
rm -rf _build deps
mix deps.get
mix compile
#+end_src

*** Tests Fail

1. Read error message carefully
2. Check if feature needs newer Elixir
3. Check if ElixirScript didn't support it
4. Document as known limitation if needed

*** Generated JS is Wrong

1. Check =priv/javascript/lib/= for runtime implementation
2. Compare with Elixir behavior in IEx
3. Add test case
4. Fix runtime or compiler
